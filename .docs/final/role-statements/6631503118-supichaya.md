## Statement (≈200 words)

I built the first version of the backend — commit `6b6922b`, "[Added] backend mvp": the package and
TypeScript setup, the Elysia app with its first routes, the domain types and initial pricing helpers, the
in-memory store, and the first tests, plus the backend documentation the rest of the team built on.

My decision was to keep the store in memory for the first cut. It let the API and the tests run with no
database, no credentials and no network, which is why the automated tests could be written from day one and
why they still run in about a second. I put the store behind an interface so the Postgres implementation could
be added later without touching the routes, which is what eventually happened.

What I would do differently: the first version authenticated staff with a single shared token. That decision
outlived the MVP — the backend still has no staff-account API, so the console verifies credentials itself, and
that is a weaker boundary than a real account table with roles. A staff-account endpoint belonged in the first
cut, not in a later sprint that never came.

Evidence: `git show --stat 6b6922b`; `backend/src/domain.ts`; `docs/backend-mvp.md`.

## Reflection

**1. Lessons learned.** *One thing that got better: getting to a running system early.* The first version of the
backend had no database — an in-memory store behind an interface — so the API and its tests ran in one second
with no credentials and no network. That meant tests existed from the first day instead of after the database
was ready, and the Postgres store could be added later without touching a single route. *One thing that got
worse: a shortcut taken early becomes the structure later.* The MVP authenticated staff with one shared token,
because it was the fastest way to make the demo work. It outlived the MVP: the backend still has no staff-account
API, so the frontend verifies credentials itself, and that is a weaker boundary than real accounts with roles
would have been. AI made that first scaffold fast to produce, and a fast scaffold looks finished — so nobody,
including me, went back to question the auth design until it was load-bearing.

**2. Where I stand in the industry today.** I am at the start, and this project showed me which part of the work
I want: the foundation other people build on. In the AI era, writing a feature is the cheap part; what is not
cheap is choosing a shape that survives — where the interface goes, where the secret lives, what the tests
assume. I want to be the person who sets that up well enough that three other people can add to it without
getting hurt by it.

**3. My plan.** Next year I want to learn Postgres properly — schema design, migrations, and what happens to
data when a business rule changes — and to work on a real service with users rather than a coursework one. In
five years I want to own a backend service end to end: its schema, its deployment, and the on-call decisions
when it breaks. I would rather understand one system deeply than ship ten I cannot explain.
